실행 추적05

인사이트 1 / 3

success: True가 “맞다”는 뜻은 아니다

“회의록을 읽고 요약해서 summary.md로 저장해줘” — 도구 호출은 전부 성공했다.

답변:        "회의록을 요약하여 summary.md에 저장했습니다"

summary.md:  "이 파일은 작업 폴더의 파일 관리 에이전트가
              수행한 작업을 요약한 것입니다…"
             ↑ 회의록이 아니라 자기 시스템 프롬프트를 요약

도구 결과:    { "success": true }  ← 검증도 통과

원인

계획은 [읽기, 요약·저장] 2단계인데 2단계가 1단계 결과를 볼 수 없었다. 각 워커는 호출될 때마다 빈 대화로 시작한다. 읽어 온 내용이 없으니 모델은 눈앞의 유일한 텍스트 — 자기 시스템 프롬프트 — 를 요약했다.

배운 것

success: True는 “쓰기가 성공했다”는 뜻이지 “쓴 내용이 맞다”는 뜻이 아니다. 가장 무서운 실패는 에러를 내지 않는다.

해결: _prior_context()로 앞 단계 결과를 다음 워커 입력에 주입

인사이트 2 / 3

잘못 건 검사

검색 결과에 환각 검사

“이 결과가 근거 자료에 기반하나?” — 그런데 검색 결과는 에이전트가 지어낸 주장이 아니라 근거 자료 그 자체다. 질문이 성립하지 않는다.

모델은 판단할 게 없으니 엉뚱한 기준(“제목과 본문이 안 맞는다”)으로 떨어뜨렸다.

인사이트 ② 평가자를 나눠라07

인사이트 3 / 3

의도 보존은 프롬프트가 아니라 자료구조 문제였다

“목록 보여주고, 그중 매출 수치 알려줘” — 계획이 [파일작업, 파일작업]으로 나온다.

// 딕셔너리로 들고 있었을 때
plan    = ["파일작업", "파일작업"]
queries = { "파일작업": "매출 수치 알려줘" }
          ↑ 뒤 단계가 앞 단계 쿼리를 덮어썼다

"목록 보여줘"가 사라지고 같은 작업이 두 번 돌았다.
// 인덱스가 일치하는 평행 리스트로
plan    = ["파일작업",    "파일작업"]
queries = ["목록 보여줘", "매출 수치 알려줘"]
          ↑ validate가 둘을 항상 같이 pop(0)

같은 뿌리의 두 번째 버그

완료 판정을 label not in plan으로 하면 중복 라벨을 구분하지 못한다. retry_num 기준으로 바꿨다 — supervisor가 작업을 넘길 때 0으로 초기화하고, validate는 재시도할 때만 올린다. 따라서 retry_num > 0이면 아직 안 끝난 것.

배운 것

교재 레퍼런스는 이 문제를 프롬프트로 방어했다. 같은 증상이 자료구조 층위에서 똑같이 나타났고, 거기서 고치는 편이 확실했다.

프롬프트로 막은 버그는 모델을 바꾸면 다시 난다.

아직 못 한 것

발표 준비 중 실행 로그에서 하나를 더 찾았다. 아래 세 번째 항목.

  • 계획은 순차 실행이다. 웹과 문서는 서로 의존이 없는데도 하나씩 돈다. 앞 장의 6.2 → 2.1초가 그대로 적용될 구간 — A2A로 분리하면 병렬화된다.
  • 벡터스토어가 인메모리다. 프로세스가 죽으면 색인이 사라진다. Chroma(persist_directory=…)로 교체하면 나머지 코드는 그대로다.
  • 체크포인터는 대화를 잇지만 증거까지 잇는다. 같은 thread_id를 쓰면 이전 질문의 검색 결과가 다음 답변의 근거에 섞인다 — 실행 로그에서 웹 4건을 찾았는데 8건으로 집계돼 발견했다. quiz_generator에서는 이게 기능이었지만(부족분만 재출제) 범용 에이전트에서는 결함이다.
